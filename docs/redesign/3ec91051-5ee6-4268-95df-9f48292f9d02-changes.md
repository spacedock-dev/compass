# Session 3ec91051: delete the summary and create it again

**Path:** 4. A session whose summary is deleted and then created again.

**Session:** Haiku 5.5 fixing the launch-grant card wording in `compass` (worktree `haiku-4892`,
draft PR #634), finished and idle. I pressed `Summarize`, read the summary, pressed `Delete summary`,
and pressed `Summarize` again. Observed on the `:4560` build of `feature/session-redesign`.

**References:** the Session Redesign design (`Main.dc.html`) and the sample session.

Severity: **P1** breaks the flow or misleads, **P2** departs visibly from the design, **P3** polish.

## First summary

1. **P2 · During the run, `Turn off summaries` sits beside `Cancel`.** Once the one-time notice has
   been seen, the running state shows `Summarizing: part 1 of 2`, "You can keep working. The summary
   will appear here.", `Cancel` and `Turn off summaries` as equal buttons. Turning off a whole
   feature is placed next to stopping this run, and is easy to press by mistake.
2. **P3 · The outline's first phase title is cut mid-word.** `"Implement <issue key>: The
   launch-grant card still says "allowed when this dashboard started" after Tu"`. Truncate at a word
   boundary with an ellipsis.
3. **P2 · The summary is good and still collapsed.** Three phases (`Checking the launch-grant flag
   on main`, `Editing the off handler and adding tests`, `Lint, typecheck, commit and draft PR`), all
   closed. The opening paragraph again starts "The person asked the agent…" and ends with the
   "(1 cited entry is an earlier check or file that Full activity does not list…)" caveat. See
   70d59c47 items 9 to 11.

## Deleting it

4. **P1 · `Delete summary` deletes with no confirmation and no undo.** One press removes a stored
   model summary that cost model calls to make. There is no "Delete this summary? It can be written
   again, which sends the session to Claude Code again", and no undo afterward. In the sample the
   same control sits beside `What is sent`, where it is easy to hit.
5. **P1 · Nothing happens for about two seconds after the press, then the card jumps.** The button
   showed no pending state. The pointer stayed on the dimmed button, then the card collapsed back to
   the pre-summary state and the content moved up under the pointer. A reader presses again and
   lands on whatever moved there (here, the outline).
6. **P2 · No message says the summary was deleted.** The card returns to its first-visit state (the
   three-sentence explanation, the estimate, `Summarize`) as if no summary had ever existed. The
   design should say "Summary deleted at 11:08. Summarize writes a new one."
7. **P3 · `Delete summary` is the most prominent control in the footer.** It is a bordered button
   ahead of two quiet disclosures. Destructive actions should be quieter than reading actions, or in
   a menu.

## Creating it again

8. **P2 · The new summary differs from the deleted one, and nothing says so.** The second run made
   four phases with different titles (`Checking main and reading the code`, `Editing the handler and
   adding tests`, `Running tests, lint and type checks`, `Committing and opening the draft PR`), and
   the opening paragraph changed wording. That is expected of a model, but a reader comparing the two
   would think the session changed. A line such as "Written again at 11:08; a new summary can group
   the work differently" would set expectations.
9. **P3 · The header switches from `updated 11:08` to `summarized at 11:08` with the model name.**
   The design's header for this card is `updated 14:27 · still running` in both states. Pick one
   format: the model name belongs with "summarized", but "updated" also appears on the outline-only
   card.
